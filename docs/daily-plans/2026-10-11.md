# Daily Plan — 2026-10-11

## Today's Goals
With only one open backlog item, today's sprint focuses entirely on #626 "Bring a cancelled tour back" — a reinstate/un-cancel capability for tours that complements the existing cancel-tour feature (CancelTourRequest/CancelTourResponse schemas, cancel endpoint in tours router) shipped in recent cycles.

## Priorities
Dev should implement a dedicated reinstate endpoint (e.g. POST /api/v1/tours/{id}/reinstate) rather than overloading the generic update endpoint, following the existing cancel-tour pattern for schema/service/router symmetry. The change must include the schema additions, a service-layer transition (cancelled → active/scheduled) with validation that only cancelled tours can be reinstated, and the route registered and wired to the router. Pagination is not relevant here since this is a single-resource state transition, not a collection endpoint.

## Risks
Main risk is a repeat of prior mismatched-PR failures: any PR claiming new schemas or service logic must actually include those files in the diff — QA should verify imported symbols (e.g. ReinstateTourRequest/Response) exist in the included schema files and that the new route is registered, not just referenced. Edge cases to cover: reinstating a tour that was never cancelled, reinstating a tour whose associated venue/date has since been double-booked, and ensuring sold-out or past-date tours aren't silently reactivated into an inconsistent state.
